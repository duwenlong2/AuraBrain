## 一、记忆的本质

### 问题 1：模型到底有没有记忆？

**答案：模型本身完全没有记忆。**

```text
你调用一次 LLM：
  模型收到 [系统提示词 + 当前对话] -> 生成回答 -> 结束
  下一轮调用：模型什么都不记得
```

这被称为 **stateless（无状态）**。模型的"知识"是训练时写死的，但**对话历史不是模型的一部分**——每次调用都是全新的。

> 官方原话（Mastra 课程）："The model is still stateless. Mastra stores context, then includes it again in later calls."
> 翻译：模型仍然是无状态的。Mastra 保存上下文，然后在后续调用中重新注入。

### 问题 2：那"记忆"到底是什么？

**记忆 = 上下文工程（Context Engineering）。**

```text
Agent 有"记忆" ≠ 模型变聪明了
Agent 有"记忆" = 每次调用前，把相关历史重新塞进上下文
```

这是理解一切记忆机制的第一性原理：

```text
你要决定"模型这一次调用能看到什么"
看到什么，它就知道什么
```

### 问题 3：为什么不能让模型"记住所有"？

因为**上下文窗口是有限的**，而且窗口越满模型表现越差。这引出两个行业公认的问题：

| 问题 | 含义 | 后果 |
| --- | --- | --- |
| **Context rot（上下文腐烂）** | 塞了太多无关历史 | 模型注意力被稀释，回答质量下降 |
| **Context waste（上下文浪费）** | 大部分历史其实不再需要 | 每轮多付大量 token 费用 |

**所有记忆方案，本质上都是在回答同一个问题：**

```text
在有限窗口里，怎么决定"该带哪些历史进去"？
```

### 问题 4：记忆的四个维度

任何记忆系统都要同时考虑这四个维度，缺一不可：

```text
① 存什么（Storage）：历史消息、结构化档案、观察记录、向量
② 取什么（Retrieval）：最近 N 条？按意思相似？按用户？
③ 怎么保持上下文小（Compression）：压缩、摘要、淘汰
④ 怎么隔离（Scoping）：每个用户/每场对话的数据不能串
```

后文所有方案，都是这四个维度的不同组合。

## 二、行业问题：为什么记忆这么难

### 问题 5：行业里最常见的记忆失败是什么？

**"记住"和"召回"是两回事。**

```text
能存下信息 ≠ 能在需要时拿出来
```

最常见的失败模式：

```text
❌ 只存不取：把所有历史存进数据库，但每次调用没把相关的找回来
❌ 只取不存：只在当前窗口里用，没持久化，重启就丢
❌ 取错对象：按时间取最近 N 条，但用户问的是 3 天前的事
❌ 窗口爆炸：无脑把所有历史都塞进去，token 爆了、质量还下降
```

### 问题 6：上下文窗口的"远距离"问题

LLM 处理长上下文有 **lost in the middle（中间丢失）** 现象：

```text
模型对开头的指令、结尾的问题记忆最好
夹在中间的大量历史，容易被忽略
```

所以"把 5000 条历史全塞进去"往往不如"精准召回 5 条最相关的"。

### 问题 7：记忆与成本的矛盾

```text
每轮都要带历史 -> token 越多 -> 钱越贵
特别是：
  工具调用结果（可能很长）
  图片/文件（token 消耗巨大）
  多轮累积
```

行业解法集中在"压缩"和"只带需要的"两个方向。

### 问题 8：记忆与隐私的矛盾

```text
记忆要持久化 -> 数据要落库 -> 隐私风险
哪些能存？存多久？谁能看？用户能删吗？
```

这是产品化的核心问题，后面专节展开。

## 三、行业主流方案全景

行业上解决 Agent 记忆，大致有这些流派（按"主动性"从低到高）：

### 流派 A：对话历史（Conversation History）

```text
原理：把最近 N 条消息原样塞进上下文
代表：几乎所有 Chat 类应用（ChatGPT 默认就是）
优点：实现最简单、逐字准确
缺点：窗口有限、跨对话失效、越久越贵
```

### 流派 B：摘要 / 滚动总结（Summarization）

```text
原理：对话太长时，用模型把旧历史压缩成一段摘要
代表：早期 ChatGPT 的"对话太长自动总结"、许多客服机器人
优点：窗口变小
缺点：摘要可能丢细节；多轮摘要后"摘要的摘要"信息衰减
```

### 流派 C：向量检索 / RAG 式召回（Semantic Recall）

```text
原理：把消息转成向量存向量库，按"意思相似"召回
代表：Mastra semanticRecall、主流 RAG 应用
优点：能跨对话、按语义找、不依赖关键词
缺点：需要 embedding 模型 + 向量库；召回质量取决于 embedding
```

### 流派 D：结构化档案（Working Memory）

```text
原理：定义一份"用户档案"模板，Agent 主动维护更新
代表：Mastra workingMemory、很多 CRM/助手类产品
优点：结构化、跨对话稳定、可被程序读取
缺点：模板要设计；Agent 可能漏更新
```

### 流派 E：分层记忆 / 长期记忆系统（如 MemGPT / Letta）

```text
原理：模仿人脑，分"主上下文（快速）"+"外部存储（长期）"
      主上下文满时，自动把旧信息"换页"到外部存储
代表：MemGPT（后改名 Letta）、一些研究系统
优点：理论上无限记忆、自动管理
缺点：复杂、重；尚未成为主流生产标配
```

### 流派 F：后台观察式记忆（Observational Memory）

```text
原理：一个后台模型（Observer）持续"观察"对话，
      自动提炼值得长期记住的事实，形成观察日志
代表：Mastra observationalMemory（较独特的设计）
优点：不用用户显式说"记住这个"；自动提炼
缺点：需要额外模型调用（成本/延迟）；提炼可能不完美
```

### 对比：各流派解决什么问题

| 流派 | 解决"当前对话连贯" | 解决"跨对话记住" | 按意思检索 | 窗口控制 | 复杂度 |
| --- | --- | --- | --- | --- | --- |
| 对话历史 | ✅ | ❌ | ❌ | ❌ | 低 |
| 摘要 | ✅ | 部分 | ❌ | ✅ | 中 |
| 语义召回 | 辅助 | ✅ | ✅ | 中 | 中 |
| 工作记忆 | 辅助 | ✅ | 部分 | ✅ | 中 |
| 分层记忆 | ✅ | ✅ | 中 | ✅ | 高 |
| 观察式记忆 | 辅助 | ✅ | 部分 | ✅ | 中高 |

> 现实产品几乎都是**组合使用**，不是单选。

## 四、Mastra 的完整方案

Mastra 把记忆拆成五个能力，官方文档原文：

```text
Message history（对话历史）     最近 N 条消息
Working memory（工作记忆）     结构化用户档案
Semantic recall（语义召回）    按意思检索历史
Observational memory（观察式记忆）后台自动提炼 + 压缩
Memory processors（记忆处理器） 上下文超限时的过滤/裁剪/优先级
```

加上辅助能力：

```text
generateTitle（标题生成）      自动给对话起标题
Threads & Resources（线程与资源） 数据隔离的组织单位
Multi-user threads（多用户线程）  多人共享一个线程
```

### 4.1 两个核心概念：Thread 和 Resource

这是 Mastra 记忆的"地基"，必须先懂：

```text
Resource（资源）= 拥有数据的实体
                 通常 = 一个用户 / 一个组织 / 一个项目
Thread（线程）  = 一场对话
```

关键规则：

```text
一个 Thread 属于一个 Resource（resourceId 不可更改）
Resource 下的所有 Thread 共享 resource 级记忆
Thread 内部是 thread 级记忆
```

```text
resource: 'user-123'
thread:   'conversation-001'
```

**理解 Scope（作用域）是关键：**

```text
scope: 'thread'    -> 只在这场对话里有效
scope: 'resource'  -> 这个用户的所有对话共享
```

### 4.2 记忆处理器（Memory Processors）

当所有记忆加起来超过上下文限制时，用处理器做**最后一公里**的过滤：

```text
Memory Processor = 一个对"将要进入上下文的记忆"做处理的函数
```

常见用途：

```text
过滤：去掉超长/无关的
裁剪：截断过长的消息
排序：按优先级重新排序
```

这回答了"窗口还是不够怎么办"的问题。

### 4.3 官方推荐的组合方式

官方明确给出分工：

```text
对话历史   -> 当前对话的连贯
语义召回   -> 按意思找回过去的相关内容
工作记忆   -> 用户的持久信息（偏好/目标/资料）
观察式记忆 -> 长对话的自动压缩 + 长期记忆
```

官方课程里给的综合配置（三件套）：

```ts
memory: new Memory({
  options: {
    lastMessages: 20,                     // 对话历史：最近 20 条
    semanticRecall: {
      topK: 3,                            // 语义召回：3 条最相似
      messageRange: { before: 2, after: 1 },
    },
    workingMemory: {
      enabled: true,
      template: `# User Profile ...`,      // 工作记忆：用户档案
    },
  },
})
```

### 4.4 观察式记忆的独特价值（重点）

官方称 OM 是 Mastra 的长上下文记忆系统，核心洞察：

```text
传统方式：历史消息越长，窗口越满，质量越差
OM 方式：后台 Observer 把旧消息压缩成"观察记录"
        观察记录替代原始历史 -> 窗口保持小、记忆保持长
```

三个关键部件：

```text
Observer（观察者）  ：从对话提取值得记住的事实
Reflector（反思者）  ：观察太多时压缩合并
Temporal markers    ：时间标记（超过 10 分钟的间隔插入提醒）
```

额外能力：

```text
Extractors（提取器）：从观察中提取结构化值（用户画像等）
Prompt caching     ：观察上下文稳定，前缀可缓存，省钱
```

## 五、专题：embedding 与中文质量问题

### 问题 9：embedding 是什么？

```text
embedding = 把一段文字变成一串数字（向量）
让"意思相近"的文字，向量也"距离近"
```

```text
"我喜欢猫"      -> [0.1, 0.3, ...]
"我超爱猫咪"    -> [0.11, 0.31, ...]   （距离近）
"我在写代码"    -> [0.9, 0.2, ...]     （距离远）
```

语义召回就是靠这个：把用户问题转向量，找历史上最相似的向量。

### 问题 10：为什么中文 embedding 质量是个问题？

这是你发现的关键问题。原因有几层：

```text
① 训练数据偏英文
   主流 embedding 模型（OpenAI text-embedding、bge-en 等）
   主要在英文语料上训练，英文效果好

② 中文分词难
   英文按空格分，中文"字/词/词组"边界模糊
   "苹果"是水果还是公司？取决于上下文

③ 中文同义表达多
   同一意思多种说法，模型没学好中文语义空间
   -> 换个说法就召回不到

④ 中文专用模型相对少
   好用的中文 embedding 模型：bge-large-zh、m3e、text2vec、bge-m3 等
   相比英文生态，选择少、迭代慢
```

### 问题 11：现在用 fastembed 的英文模型，中文效果如何？

```text
能用，但"凑合"：
  - 英文模型对中文也产生向量（不是不能工作）
  - 但中文语义区分度低，容易：
    召回不到（相关没找回）
    召回错（无关的却相似度高）
  - 我们在 04-memory 里实测：简单的"出差/转换插头"能召回
    因为内容高度相关；复杂、抽象的中文可能失准
```

**结论：学习阶段用 fastembed 完全够（免费、本地、能跑通机制）；产品阶段对中文要认真选 embedding。**

### 问题 12：产品里中文 embedding 怎么选？

分三个层次：

```text
层次 1：本地免费（适合学习/原型/离线）
  - @mastra/fastembed（bge-small-en / bge-base-en）
  - 中文可用但精度一般

层次 2：本地中文专用（适合有中文需求、可接受稍重依赖）
  - BGE 中文系列：bge-large-zh、bge-m3（多语言，中文好）
  - M3E：m3e-base、m3e-large（中文社区常用）
  - text2vec 系列
  - 通过 @mastra/fastembed 的 FlagEmbedding 或自定义 embedder 接入

层次 3：云端中文友好（适合产品，效果好、要 API key + 花钱）
  - OpenAI：text-embedding-3-small / large（多语言，中文可以）
  - 阿里：text-embedding-v3（中文电商/通用场景强）
  - 智谱：embedding-3
  - 硅基流动/其他：bge-m3 等开源模型的托管版
```

**选型建议：**

```text
先小规模测：用你的真实中文数据，测"换个说法能否召回"
对比几个模型：召回率 + 成本 + 延迟
不要只看榜单分数，要用你的业务场景测
```

### 问题 13：embedding 维度、距离度量、阈值怎么定？

```text
维度（dimensions）：
  越高越准但越慢越贵（bge-small 384，bge-large 1024）
  有些模型支持动态维度（如 OpenAI 可裁剪）

距离度量（metric）：
  cosine（余弦）最常用，适合语义相似
  dotproduct（点积）适合已归一化向量，速度更快

阈值（threshold）：
  Mastra semanticRecall.threshold 默认 0.3
  太高 -> 什么也召回不到
  太低 -> 召回一堆无关
  需要根据你的 embedding 模型实测调
```

### 问题 14：语义召回 vs 关键词检索，谁更好？

```text
语义召回（向量）：
  + 能处理同义/换说法
  + 跨语言/跨表达
  - 需要 embedding + 向量库
  - 精确术语/编号匹配弱（如订单号"AB-123"）

关键词检索（如 FTS 全文搜索）：
  + 精确匹配强（编号、专有名词）
  - 换说法就找不到

行业实践：两者结合（hybrid search）
  关键词过滤候选 -> 语义排序
  或 语义召回 + 元数据过滤（Mastra semanticRecall.filter 支持）
```

Mastra 的 `filter`（元数据过滤）就是为此设计的：

```ts
semanticRecall: {
  scope: 'resource',
  filter: { projectId: { $eq: 'project-a' } },
}
```

## 六、专题：产品化记忆要考虑什么

### 问题 15：产品里"记忆"要做成什么样？

一句话：**记忆是产品体验的一部分，不是技术噱头。**

好的记忆产品：

```text
用户感受到"它记得我"
但不觉得"它在偷窥我"
```

产品化要回答：

```text
① 记什么：用户明确说的偏好？行为推断？都记？选择性记？
② 记多久：永久？会过期？（记忆保鲜）
③ 怎么展示：用户能看到/编辑/删除自己存的信息吗？
④ 怎么纠错：记错了怎么改？
⑤ 一致性：跨设备/跨对话是否同步？
```

### 问题 16：记忆的"保鲜"问题

```text
用户上个月说"我喜欢咖啡"，这个月改喝茶了
旧记忆如果不清除，会一直误导
```

行业做法：

```text
覆盖式更新：新信息覆盖旧的（workingMemory merge 语义支持）
时间衰减：太久没重申的记忆降低权重
人工确认：关键偏好让用户确认
定期回顾：让 Agent 定期检查记忆是否还成立
```

### 问题 17：记忆与"遗忘"（用户有权利被遗忘）

GDPR 等法规要求用户可删除数据。产品必须：

```text
提供"清除记忆"功能
删除时：删线程 + 删消息 + 删向量 + 删工作记忆 + 删观察记录
（Mastra 提供 deleteThread 等 API，但要自己串起来调）
```

**这是产品必做项，不是可选项。**

### 问题 18：记忆的可解释性

```text
用户/开发者需要知道：Agent 这次为什么这么答？
  -> 因为召回了哪条记忆？
```

做法：

```text
用 Observability/Traces 看：这次调用注入了哪些记忆
对用户展示"我记着你的这些信息"
这既提升信任，也方便调试
```

### 问题 19：冷启动问题

```text
新用户没有历史记忆 -> Agent 表现"陌生"
```

做法：

```text
引导性问题主动收集（"你平时几点上班？"）
允许用户导入/手动填写偏好
用模板默认值（workingMemory template 预填常见字段）
```

## 七、专题：多用户与安全

### 问题 20：多用户时怎么隔离数据？

这是你之前判断"需要业务系统才学"的部分，但记忆这块必须提前知道：

```text
核心：用 resourceId 隔离
  每个用户一个 resourceId
  resource-scoped 记忆天然按用户隔离
```

官方明确警告：

```text
"Memory 系统本身不强制访问控制。
 在查询前，必须由你的应用逻辑校验当前用户是否有权访问该 resourceId。"
```

**即：隔离靠"你给每个请求传对 resourceId"，权限校验靠你的业务层。**

### 问题 21：多用户共享一个线程（Multi-user threads）

用于协作场景（文档协作、群聊）：

```text
多个用户共享同一个 resourceId + threadId
用 <turn> 标签在消息里标记说话人身份
```

```text
<turn author_id="u_alice" author_name="Alice" functional_role="editor">
  这段文字要改成...
</turn>
```

**安全红线（官方特别强调）：**

```text
speaker 身份必须来自你认证后的请求上下文
绝不能来自请求体！
否则客户端能伪造 author_id 冒充别人
```

### 问题 22：记忆的权限分层

```text
能看这条记忆的人 = 能访问该 resourceId 的人
```

产品里的常见分层：

```text
用户级：只能看自己的
项目级：项目成员共享（resource = project-42）
组织级：组织内共享
```

需要结合 Request Context / Auth 在业务层实现。

## 八、专题：成本、性能与隐私

### 问题 23：记忆的成本怎么控制？

```text
成本来源：
  每次调用带的历史 token
  OM 的 Observer/Reflector 模型调用
  标题生成（每次异步一次）
  提取器（额外结构化输出）
```

省钱策略：

```text
① 用更小的模型做记忆相关任务（OM 的 Observer、标题生成）
   Mastra 支持给 OM/标题指定小模型
② lastMessages 别开太大（10~20 够用）
③ topK 别太大（3~5）
④ 用 OM 压缩历史，减少每轮 token
⑤ prompt caching：OM 稳定上下文可缓存
```

### 问题 24：记忆的性能（延迟）影响

```text
每轮调用前的记忆步骤：
  读历史（快，数据库）
  语义召回（embedding + 向量查询，需要时间）
  OM 观察（后台，通常不阻塞）
```

Mastra 实测经验（02 项目已验证）：

```text
memory recall / save 只要 0~12ms
大头永远是 LLM 调用
本地 embedding（fastembed）通常也快
云端 embedding 会增加一次网络往返
```

**记忆本身不是性能瓶颈，模型调用才是。**

### 问题 25：敏感信息怎么处理？

```text
记忆会存下用户说的话 -> 可能含敏感信息
```

做法：

```text
① 存储加密（数据库层）
② 敏感数据过滤（Mastra 的 SensitiveDataFilter 用于观测，不用于记忆存储）
③ 业务层决定：哪些信息不进记忆（在 instructions 里禁止 Agent 记住）
④ 给用户删除权（见"遗忘"问题）
⑤ 不要存明文密码/密钥（记忆系统不适合存 secret）
```

## 九、决策速查表

### 场景 -> 该用哪种记忆

| 你的场景 | 推荐方案 |
| --- | --- |
| 只想让当前对话连贯 | 对话历史（默认够） |
| 要跨对话记住用户偏好 | 工作记忆（结构化）或观察式记忆（自动） |
| 要按"意思"找回过去内容 | 语义召回（需要 embedding + 向量库） |
| 长对话窗口不够了 | 观察式记忆 + 记忆处理器 |
| 多人协作同一话题 | 多用户线程 + <turn> 标签 |
| 要给对话起标题 | generateTitle |

### 记忆组合公式（产品常见）

```text
对话历史（基础连贯）
+ 工作记忆（用户档案）
+ 语义召回（需要时按意思检索）
+ （可选）观察式记忆（长对话自动压缩）
```

### 中文场景特别注意

```text
产品级中文语义召回：
  优先用中文友好 embedding（bge-large-zh / bge-m3 / 阿里 / 智谱）
  用真实数据测"换说法召回"
  配合关键词检索 + 元数据过滤（hybrid）
```
